参赛开发重点
- user_agent.py 是正式评测加载选手实现的核心文件。
- ReasoningAgent 需要支持由平台注入官方 client，不应在代码中硬编码 API Token。
- solve(problem: str, metadata: dict) -> dict 必须返回可 JSON 序列化的字典，并包含非空字符串字段 final_response。

- 本地样例数据中的 answer 只用于调试对照，正式评测不会向选手代码提供标准答案。

本文档为挑战杯人工智能赛道初赛赛题文档，面向参赛选手说明本赛题的任务目标、baseline 仓库的作用、智能体接口规范、输入输出格式、代码提交方式以及自动判分系统的基本工作流程。
1. 赛题简介
本赛题围绕 Intern-S 系列模型的数学智能体设计与推理创新展开。选手需要设计一个能够解决数学问题的推理智能体。智能体接收一道数学题文本，结合题目元信息进行推理，并输出最终答案。
选手的核心任务是实现：
agent.solve(problem: str, metadata: dict) -> dict
平台会在正式评测时读取实际测试题，调用选手提交代码中的该入口函数，取得 final_response，并结合官方 judger 与标准答案进行判分。
本赛题鼓励选手探索不同的智能体设计方式，包括但不限于：
- 提示词设计与多轮推理
- 多候选生成、验证与选择
- 规划、反思、纠错、答案格式化
- 工具调用、检索、记忆或其它推理策略
- 面向数学题的专门解析、符号计算或后处理
最终评分主要依据 final_response 的答案正确性。trace 可用于记录智能体的推理与交互过程，便于异常排查、结果展示和同分情况下的设计质量参考。
2. Baseline 仓库说明
Baseline 仓库地址：https://github.com/InternLM/Challenge-Cup-2026
本仓库提供一个 naive agent baseline，作用是帮助选手理解：
- 赛题内容与本地调试方式
- 输入数据格式
- 智能体入口函数
- 智能体输出格式
- 平台 runner 与选手代码之间的调用关系
baseline 只是一个最小可运行示例，不限制选手的具体实现。选手可以保留、修改或替换其中的智能体逻辑，也可以新增模块、工具和依赖。但正式提交的仓库必须满足平台约定的入口规范。
必须包含的文件
选手提交的仓库根目录必须包含：
user_agent.py
平台 runner 会从该文件中加载选手实现。其它文件可以根据需要添加，例如：
requirements.txt
tools/
prompts/
utils/
但所有新增文件都应使用相对路径读取，不要依赖本地机器上的绝对路径。
user_agent.py 必须遵守的规范
user_agent.py 中必须提供类：
class ReasoningAgent:
    ...
平台会使用官方 client 初始化该类：
from user_agent import ReasoningAgent

agent = ReasoningAgent(client=official_client)
因此 ReasoningAgent 至少需要支持如下构造方式：
def __init__(self, client, *args, **kwargs):
    ...
其中 client 由平台提供。选手不要在代码中写死 API key，也不要假设本地存在固定的 API 配置文件。正式评测时，模型访问、限流、token 统计、超时控制等由官方 client 和平台 runner 统一管理。
评测时平台提供的 client 与 baseline 中 llm_client.py 的 InternChatClient 结构一致，可作为本地实现参考。选手可以参考其中的 chat(messages, temperature, max_tokens) 调用方式组织模型请求：
response = client.chat(messages=[
        {"role": "user", "content": problem},
    ],
    temperature=0.2,
    max_tokens=4096,
)
ReasoningAgent 必须提供推理函数：
def solve(self, problem: str, metadata: dict) -> dict:
    ...
输入参数含义如下：
- problem: 数学题题面文本。
- metadata: 题目元信息字典，至少可能包含 idx。正式评测时，metadata 的具体字段以平台 runner 为准。选手代码不得依赖 answer、标准答案或隐藏评测数据。
返回值必须是 dict，且必须包含非空字符串字段：
{
  "final_response": "最终答案"
}
推荐同时返回 trace：
{
  "final_response": "最终答案",
  "trace": [
    {"step": "plan", "content": "..."},
    {"step": "model_call", "content": "..."},
    {"step": "finalize", "content": "..."}
  ]
}
字段要求：
- final_response 必须是可读的最终答案，不能为空。
- trace 可选，建议为列表，记录关键推理步骤、模型调用摘要、候选答案、验证过程等。
- 返回内容必须可以被 JSON 序列化。
- 不要在 trace 中写入 API key、访问令牌、个人隐私信息或其它敏感内容。
实现自由度
选手可以使用 baseline 中的 lagent 示例，也可以完全不用 lagent。平台只要求 user_agent.py 暴露符合规范的 ReasoningAgent 和 solve 方法。
选手可以新增辅助函数、类和模块，也可以在 ReasoningAgent 内部维护状态。但需要注意：
- 不要依赖评测题之间的固定顺序。
- 不要假设多个题目一定在同一个进程中运行。
- 不要依赖本地绝对路径。
- 不要读取或构造隐藏测试集、标准答案或 judger 信息。
- 不要在代码中硬编码 API key。
- 不要输出恶意内容、执行破坏性操作或规避平台资源限制。
3. 输入数据与输出样例
本地调试输入为 JSONL 文件，每行是一道题。每行至少包含：
{"idx": 0, "problem": "题目文本"}
样例：
{"idx": 0, "problem": "设$\\mathbb{F}_{81}$为$81$元的有限域。$T=\\{\\alpha\\in\\mathbb{F}_{81}|\\mathbb{F}_{81}=\\mathbb{F}_3(\\alpha)\\}$。求$T$中元素的个数。", "answer": "72", "subject": "抽象代数", "source": "sample"}
其中 answer 只会出现在样例数据中，用于选手本地对照调试。正式评测不会向 solve 传入标准答案。
本地 runner 会将每道题的结果保存为独立 JSON 文件：
outputs/
  0.json
  1.json
  2.json
成功输出样例：
{
  "idx": 0,
  "status": "success",
  "final_response": "72",
  "trace": [
    {
      "step": "solve",
      "content": "有限域 F_81 是 F_3 上 4 维扩张，生成整个扩张的元素个数为 81 - 9 = 72。"
    }
  ]
}
异常输出样例：
{
  "idx": 0,
  "status": "error",
  "final_response": "",
  "error": {
    "type": "RuntimeError",
    "message": "错误信息"
  },
  "trace": []
}
本地调试时，如果某个 idx.json 已经存在且文件非空，runner 会跳过该题，便于中断后继续运行。
4. 本地调试建议
安装依赖：
pip install -r requirements.txt
设置 API key：
export INTERN_API_KEY="sk-..."
运行样例：
python main.py --input_file sample_data/dev.jsonl --output_dir sample_outputs
本地 runner 默认并发数为 8。如需调整：
export LOCAL_MAX_CONCURRENCY=4
本地调试结果只用于选手自测，不代表正式评测分数。正式评测会使用隐藏测试集、官方 client、平台 runner 和官方 judger。
5. Intern-S API 使用说明
选手可以使用报名挑战杯时填写的手机号注册书生 API 控制台：
https://internlm.intern-ai.org.cn/api/document
书生 API 控制台中的 API 均可免费使用。平台会对普通用户执行流控策略：
RPM 30
TPM 150000
如果本地调试或实验需要更高流控，可以前往以下页面申请提升：
https://internlm.intern-ai.org.cn/api/strategy
申请时请在备注中填写“挑战杯”。通常情况下，200 RPM 以内的流控提升会在 1-2 个工作日内生效。具体生效时间以 API 控制台状态为准。
选手可以使用 API 控制台下的任意可用模型作为智能体 base model，例如：
- intern-s1
- intern-s1-pro
- intern-s2-preview
本地使用 baseline runner 调试时，可以通过环境变量指定模型：
export INTERN_MODEL="intern-s2-preview"
如需调整 API endpoint，请以书生 API 控制台文档中的接口地址为准配置 INTERN_API_BASE。
提交仓库至评分系统时，选手可以选择智能体实际使用的模型。正式评测时，平台 runner 会通过官方 client 使用该模型进行调用。
评分系统 client 使用的 API 来自书生 API 控制台：
https://internlm.intern-ai.org.cn/api
建议选手本地调试时也使用同一份 API 控制台，避免本地实验环境和正式评分环境之间产生模型行为、接口格式或网关策略差异。
6. 赛题提交方式
参赛队伍可以在 2026-06-30 报名结束后 (2026-7-01 起) 开始提交作品进行判分，选手需要基于 baseline 仓库准备自己的提交代码，并向判分系统提交仓库地址与 commit SHA。
推荐流程：
1. fork baseline 仓库代码并将 fork 的仓库 clone 到本地。
2. 在自己的仓库中完成实现。
3. 确保仓库根目录包含符合规范的 user_agent.py。
4. 将代码推送到 github (fork 的仓库或者自己的私有仓库均可)。
5. 在判分系统中完成仓库授权。
6. 向判分系统提交仓库地址和 commit SHA。
关于仓库可见性：
- 如果直接 fork 一个公开 baseline 仓库，fork 和提交内容通常也是公开可见的。
- 如果不希望自己的方案公开，建议将 baseline clone 到本地后，推送到自己的 private repository。
- 选手也可以保持仓库公开，但需自行承担方案被其他人看到的风险。
判分系统会以选手提交的 commit SHA 作为评测快照。请务必提交具体 commit SHA。
最终提交
初赛截止前，请根据挑战杯官网要求，将自己的最终版本代码仓库与赛题要求的其它材料打包成 .zip 文件发送邮件至：
changshuai@pjlab.org.cn
建议压缩包内至少包含：
- 最终版本代码。
- user_agent.py 及所有运行所需的辅助文件。
- requirements.txt 或其它依赖说明。
- 一份说明文件，写明队伍信息、题目名称、仓库地址、分支名称、commit hash 和选择使用的模型。
提交前建议检查：
- user_agent.py 可以被正常 import。
- ReasoningAgent(client=official_client) 可以正常初始化。
- solve(problem, metadata) 返回包含非空 final_response 的字典。
- 所有依赖都已写入 requirements.txt。
- 代码中没有硬编码 API key、个人路径、临时文件路径或调试用标准答案。

后续自动判分系统的基本工作流程如下：
1. 选手在系统中提交仓库地址与 commit SHA。
2. 系统检查仓库授权，并拉取对应 commit 的代码。
3. 系统在隔离环境中安装依赖并加载 user_agent.py。
4. 系统根据选手提交时选择的模型，使用官方 client 初始化 ReasoningAgent。
5. 平台 runner 读取正式评测题，调用 agent.solve(problem, metadata)。
6. 系统收集 final_response、trace、运行耗时、异常信息和资源使用情况。
7. 官方 judger 结合标准答案对结果进行判分。
8. 系统返回最终分数以及是否存在异常。
正式评测时：
- 平台会使用官方闭源测试集。
- 平台会使用来自书生 API 控制台的官方 client，不使用选手自带 API key。
- 平台会统一控制超时、并发、模型调用预算和资源限制。
- 平台不会向选手返回逐题题目、标准答案、judger 细节或逐题详细反馈。
- 如果代码无法安装、无法 import、入口函数不符合规范、运行超时、输出格式错误或触发安全策略，系统会标记异常。
8. 初赛评分与晋级
初赛完全采取客观评分方式对所有参赛队伍进行排名。排名依据为初赛截止日期时，判分系统榜单上的队伍最终排名。
在初赛截止日期前，组委会会根据整体赛题完成质量、参赛队伍分数分布等情况，公布进入决赛的最低分数线。进入决赛的队伍数量少于 30 支，具体晋级名单以赛事官方通知为准。
9. 提交次数限制
从判分系统上线日到初赛截止时间，每支队伍的提交次数限制为：
- 每天最多提交 2 次 ---> 定时出分 (12:00，最新的提交刷新分数)
- 每周最多提交 10 次。
判分系统只会给出最终分数以及是否存在异常。请选手在本地充分调试后再提交正式评测，避免因格式错误、依赖缺失或超时浪费提交次数。
10. 常见异常
以下情况可能导致判分异常：
- 仓库授权失败，系统无法拉取提交。
- 提交的是分支名而不是 commit SHA。
- user_agent.py 不存在。
- ReasoningAgent 类不存在或构造函数不接受 client。
- solve 方法不存在、签名不符合要求或抛出异常。
- 返回值不是字典。
- final_response 缺失、为空或不是字符串。
- 返回值无法 JSON 序列化。
- 依赖无法安装或版本冲突。
- 运行超时或资源使用超过平台限制。
- 代码依赖本地绝对路径、私有文件或未声明资源。
- 代码包含硬编码密钥、恶意行为或规避评测限制的逻辑。
11. 选手实现建议
为了提高提交稳定性，建议选手：
- 保持入口接口简单稳定，把复杂逻辑封装到内部模块。
- 对模型输出做答案抽取和格式化，避免 final_response 过长或答案不明确。
- 对异常进行适度处理，保证单题失败不会影响整体运行。
- 控制模型调用次数和 token 使用，避免超时。
- 在本地使用样例数据完整跑通安装、初始化、推理和输出保存流程。
- 保留清晰的 trace，但不要记录敏感信息。
本仓库的 baseline 仅用于说明接口和基本思路。正式比赛欢迎选手提交更强、更稳定、更有创造性的数学智能体实现。

你将完成什么
本地快速开始包含四件事：
1. 准备 Python 3.10+ 环境并安装依赖。
2. 配置书生 API 访问所需的环境变量。
3. 使用 sample_data/dev.jsonl 跑通 baseline。

Baseline 目录关系
快速开始阶段主要关注 challenger_agent_baseline 目录：
challenger_agent_baseline/
  main.py                 # 本地样例 runner：读取 JSONL，逐题写出 JSON
  llm_client.py           # 本地样例 API client：读取 INTERN_* 环境变量
  user_agent.py           # 参赛选手主要修改文件
  requirements.txt        # baseline 依赖
  sample_data/dev.jsonl   # 本地样例输入，共 3 道题
各文件的职责如下：
- main.py：读取输入 JSONL，为每道题调用 ReasoningAgent.solve(problem, metadata)，再把结果写入 output_dir/{idx}.json。
- llm_client.py：读取 INTERN_API_KEY、INTERN_API_BASE、INTERN_MODEL，用 OpenAI-compatible chat completions 形式请求模型。
- user_agent.py：baseline 的智能体实现，当前示例使用 lagent 组织 generate-verify-select 流程。正式参赛时，你主要在这个文件中改进智能体。
- sample_data/dev.jsonl：本地自测样例。样例中可能带有 answer 便于人工对照，正式评测不会把标准答案传入智能体。

Finished idx=0
Finished idx=1
Finished idx=2

成功标准
一次本地试跑是否成功，不看终端里是否只打印了 Finished，而要检查输出 JSON：
- sample_outputs/0.json、sample_outputs/1.json、sample_outputs/2.json 均已生成。
- 每个文件的 status 都是 success。
- 每个文件的 final_response 都是非空字符串。
- trace 如果存在，应为可 JSON 序列化的列表。
可以用下面命令快速检查：
find sample_outputs -maxdepth 1 -name '*.json' -print | sort
jq -r '"\(.idx)\t\(.status)\tfinal_response_len=\(.final_response | length)"' sample_outputs/*.json
如果没有安装 jq，可以使用 Python：
python - <<'PY'
import json
from pathlib import Path

for path in sorted(Path("sample_outputs").glob("*.json")):
    data = json.loads(path.read_text(encoding="utf-8"))
    print(path.name, data.get("status"), len(data.get("final_response", "")))
PY

环境准备与依赖安装

本页说明如何准备本地运行环境，重点避免 Python 版本、虚拟环境、依赖安装、API 环境变量带来的入门阻塞。建议先完成本页，再运行 baseline。
环境要求
推荐环境：
- Python 3.10 或更高版本。
- macOS、Linux 或 Windows WSL。
- 可以访问 Python 包源和 GitHub。requirements.txt 中的 lagent 会从 GitHub 指定 commit 安装。
- 可以访问书生 API 服务。
- 有足够磁盘空间安装依赖。依赖中包含 ray 等体积较大的包，安装时间可能较长。
不建议使用 Python 3.8。baseline 和依赖中使用了较新的类型语法，Python 3.8 可能在导入 lagent 或 user_agent.py 时触发兼容错误，例如 unsupported operand type(s) for |。
创建虚拟环境
进入 baseline 目录：
cd challenger_agent_baseline

python3.10 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
确认当前 Python 版本：
python --version
输出应为 Python 3.10.x 或更高版本。
如果系统 Python 提示 externally-managed-environment，不要强行向系统环境安装依赖。可以改用 uv 创建隔离环境：
uv venv --python 3.10 .venv
source .venv/bin/activate
python -m pip install --upgrade pip
如果你的系统中 python3.10 不存在，请先通过系统包管理器、conda、pyenv 或团队统一环境安装 Python 3.10+。
安装依赖
在 challenger_agent_baseline 目录中执行：
python -m pip install -r requirements.txt
安装完成后，可以做一个轻量检查：
python - <<'PY'
import lagent
import requests

print("lagent import ok")
print("requests import ok")
PY
如果这里失败，先不要运行 main.py，应优先解决依赖安装问题。
常见处理方式：
- GitHub 访问失败：检查网络或代理配置，然后重新执行安装命令。
- 包下载过慢：切换可用的 Python 包源，但不要改动 requirements.txt 后直接提交。
- 磁盘空间不足：清理 pip 缓存或换到空间更充足的环境。
- ray 等大依赖安装失败：先确认 Python 版本、操作系统架构和磁盘空间。
配置 API 环境变量
llm_client.py 会从环境变量读取 API 配置：
- INTERN_API_KEY：必填，你自己的 API Token。
- INTERN_API_BASE：可选，默认值为 https://chat.intern-ai.org.cn/api/v1/chat/completions。
- INTERN_MODEL：可选，默认值为 intern-s2-preview。
- LOCAL_MAX_CONCURRENCY：可选，本地 runner 并发数，默认值为 8。
首次试跑建议显式设置低并发：
export INTERN_API_KEY="替换为你自己的 API Token"
export INTERN_MODEL="intern-s2-preview"
export LOCAL_MAX_CONCURRENCY=1
通常不需要设置 INTERN_API_BASE。如果确实需要覆盖，可以这样写：
export INTERN_API_BASE="https://chat.intern-ai.org.cn/api/v1/chat/completions"
安全注意事项：
- 不要把 API Token 写入 user_agent.py、llm_client.py 或任何会提交的文件。
- 不要把 API Token 粘贴到公开 Issue、群聊截图、文档或 trace 中。
- 终端中的 export 只对当前 shell 会话生效。新开终端后需要重新设置，或使用你自己的安全密钥管理方式。
- 如果 Token 过期或 401 鉴权失败，请重新生成或复制 Token，不要在文档中保存旧 Token。

跑通 Baseline 与检查输出

本页说明如何使用 baseline 的本地 runner 运行样例数据，并判断结果是否符合提交前的基本格式要求。本地样例结果只用于自测，不代表正式评测分数。
运行命令
进入 baseline 目录并激活虚拟环境：
cd challenger_agent_baseline
source .venv/bin/activate
首次运行建议低并发：
export LOCAL_MAX_CONCURRENCY=1
确认已经设置自己的 API Token 后运行样例：
python main.py --input_file sample_data/dev.jsonl --output_dir sample_outputs
本地 runner 会读取 sample_data/dev.jsonl 中的 3 道样例题，并把输出写入 sample_outputs。
Runner 会做什么
main.py 的执行流程如下：
1. 读取输入 JSONL，每个非空行是一道题。
2. 如果某行没有 idx，使用行号作为默认 idx。
3. 初始化 InternChatClient 和 ReasoningAgent。
4. 为每道题调用 ReasoningAgent.solve(problem, metadata)。
5. 校验 solve 返回值中的 final_response 是非空字符串。
6. 将每道题的结果写入 output_dir/{idx}.json。
7. 如果某个 {idx}.json 已经存在且非空，跳过该题，便于中断后继续运行。
runner 默认并发数为 8，由 LOCAL_MAX_CONCURRENCY 控制。首次验证链路时建议设置为 1；确认稳定后，再根据 API 流控和你的智能体调用次数逐步调高。
样例输入格式
sample_data/dev.jsonl 每行是一道题，至少包含：
{"idx": 0, "problem": "题目文本"}
样例数据可能额外包含：
- answer：本地人工对照用的参考答案。
- subject：题目所属方向。
- source：样例来源标记。
你的 solve(problem, metadata) 只应依赖题面和平台传入的元信息，不要把样例中的 answer 当作正式评测可用字段。正式评测不会向智能体提供标准答案。
终端输出
正常开始运行时，终端会先打印读取数量和并发数：
Loaded 3 items. Max concurrency: 1.
每道题处理完成后，会打印：
Finished idx=0
Finished idx=1
Finished idx=2
最后打印输出目录：
Saved outputs to sample_outputs
这些日志只说明 runner 已经为对应 idx 写出文件。最终是否成功，还要看 JSON 文件中的 status、final_response 和 error 字段。
如果你重复运行同一个输出目录，且旧文件非空，可能看到：
Skip idx=0 because sample_outputs/0.json already exists.
这表示 runner 复用了已有输出。想重新生成结果时，请删除旧输出目录或换一个新的 --output_dir。
输出文件格式
成功输出应类似：
{
  "idx": 0,
  "status": "success",
  "final_response": "智能体对该题的最终答案",
  "trace": [
    {
      "step": "policy_call_0",
      "content": {
        "message": "题目与提示词摘要",
        "response": "候选解答"
      }
    }
  ]
}
失败输出应类似：
{
  "idx": 0,
  "status": "error",
  "final_response": "",
  "error": {
    "type": "RuntimeError",
    "message": "Chat completion failed after 3 attempts: ..."
  },
  "trace": []
}
字段含义：
- idx：题目编号，来自输入数据或行号。
- status：success 表示 solve 返回了合法结果；error 表示该题处理时抛出异常。
- final_response：最终答案。正式评分主要依据这个字段。
- trace：推荐记录推理过程、候选答案、验证和选择步骤，必须可 JSON 序列化。
- error：仅失败时出现，包含异常类型和信息。
检查是否跑通
先检查文件数量：
find sample_outputs -maxdepth 1 -name '*.json' -print | sort
期望看到：
sample_outputs/0.json
sample_outputs/1.json
sample_outputs/2.json
再检查状态和答案长度：
jq -r '"idx=\(.idx) status=\(.status) final_response_len=\(.final_response | length)"' sample_outputs/*.json
所有文件都应满足：
- status=success。
- final_response_len 大于 0。
- 没有 error 字段，或 error 为空。
如果没有安装 jq，可以使用 Python 检查：
python - <<'PY'
import json
from pathlib import Path

ok = True
for path in sorted(Path("sample_outputs").glob("*.json")):
    data = json.loads(path.read_text(encoding="utf-8"))
    status = data.get("status")
    response = data.get("final_response", "")
    error = data.get("error")
    print(f"{path.name}: status={status}, final_response_len={len(response)}")
    if error:
        print(f"  error={error}")
    ok = ok and status == "success" and isinstance(response, str) and bool(response.strip())

raise SystemExit(0 if ok else 1)
PY
如果命令退出码为 0，说明样例输出满足快速开始的基本格式要求；如果退出码为 1，请查看打印出的 error 信息并参考本地调试常见问题。
没有生成输出文件
如果命令很快退出，且 sample_outputs 中没有生成题目 JSON，优先看终端错误。常见情况包括：
- RuntimeError: Missing API key. Set INTERN_API_KEY.：当前 shell 没有设置 INTERN_API_KEY，client 初始化失败。
- ModuleNotFoundError: No module named 'lagent'：依赖没有安装到当前 Python 环境。
- Python 类型语法兼容错误：当前 Python 版本过低，建议换到 Python 3.10+。
- 输入文件路径错误：确认当前目录是 challenger_agent_baseline，并且 sample_data/dev.jsonl 存在。
这类错误发生在单题处理前，runner 可能还没有机会写出 {idx}.json。
检查单个错误
当某个输出文件的 status 是 error 时，说明 runner 已经进入单题处理，但 solve 或模型请求过程中抛出了异常。先查看错误类型和信息：
jq '.error' sample_outputs/0.json
常见方向：
- 401 Unauthorized 或鉴权失败：Token 无效、过期、复制错误或账号权限不匹配。
- Chat completion failed after 3 attempts：模型请求连续失败，继续看后面的 HTTP 状态或服务返回信息。
- ValueError: agent.solve must return a non-empty string field: final_response：你的 solve 返回缺少非空 final_response。
- TypeError: Object of type ... is not JSON serializable：返回结果或 trace 中包含不能写入 JSON 的对象。
跑通后做什么
跑通 baseline 后，可以开始改进智能体：
1. 打开 user_agent.py。
2. 在 PARTICIPANT DESIGN AREA 标记之间修改提示词、采样、验证、选择和 trace 记录逻辑。
3. 保持 ReasoningAgent 类名、构造方式和 solve(problem, metadata) 方法可被 runner 调用。
4. 每次修改后，用新的输出目录做一次快速回归，例如：
python main.py --input_file sample_data/dev.jsonl --output_dir sample_outputs_v2
不要只看样例题答案是否碰巧正确，也要检查输出格式、异常处理和 trace 是否稳定。正式评测会使用隐藏测试集、官方 client、平台 runner 和官方 judger。

本地调试常见问题

本页收集快速开始阶段最常见的 baseline 本地运行问题。这里重点处理环境、依赖、API 鉴权、流控和输出格式；更完整的比赛问答会沉淀在 FAQ 页面。
Missing API key. Set INTERN_API_KEY.
原因：当前 shell 没有设置 INTERN_API_KEY，llm_client.py 无法初始化本地 API client。
处理方式：
export INTERN_API_KEY="替换为你自己的 API Token"
然后重新运行：
python main.py --input_file sample_data/dev.jsonl --output_dir sample_outputs
如果你新开了一个终端，需要重新设置环境变量。不要把 Token 写进 user_agent.py、llm_client.py 或提交包。
401 Unauthorized / 用户鉴权失败
常见原因：
- Token 复制不完整，包含多余空格或换行。
- Token 已失效或已被重置。
- 当前账号、服务或模型权限不匹配。
- 手动设置了错误的 INTERN_API_BASE。
处理方式：
1. 重新从 API 控制台复制自己的 Token。
2. 在当前 shell 中重新执行 export INTERN_API_KEY="..."。
3. 如果你设置过 INTERN_API_BASE，先取消覆盖，使用默认地址：
unset INTERN_API_BASE
1. 使用低并发重新试跑：
export LOCAL_MAX_CONCURRENCY=1
python main.py --input_file sample_data/dev.jsonl --output_dir sample_outputs_retry
baseline 的 llm_client.py 会自动把不带 Bearer  前缀的 Token 转成 Authorization: Bearer ...。你只需要保证环境变量中是自己的有效 Token，不要在文档或日志中暴露密钥内容。
Token 过期
现象可能是服务返回 token expired、A0211 token 过期、401 Unauthorized 或类似鉴权错误。
处理方式：
- 前往 API 控制台重新生成或获取有效 Token。
- 在当前 shell 中重新设置 INTERN_API_KEY。
- 删除旧失败输出目录，或指定新的 --output_dir 后重跑。
注意：Token 通常只应由你本人保存和使用。不要把过期 Token 或新 Token 粘贴到公开文档、群聊、Issue、trace 或提交文件中。
-20053 / 超出频率限制
原因：请求频率或 token 用量超过当前流控。baseline 默认本地并发为 8，而当前 user_agent.py 对每道题会多次调用模型：生成多个候选，再对候选进行验证。并发和多次采样叠加后，首次运行更容易触发流控。
处理方式：
export LOCAL_MAX_CONCURRENCY=1
python main.py --input_file sample_data/dev.jsonl --output_dir sample_outputs_low_concurrency
如果你已经修改过 user_agent.py，还可以临时降低：
- policy_sample_times：候选生成次数。
- verifier_voting_times：验证投票次数。
- 单次请求的 max_tokens。
确认链路稳定后，再按实验需要逐步增加并发或调用次数。
Python 版本相关错误
典型现象：
unsupported operand type(s) for |: 'type' and 'NoneType'
或在导入 lagent、user_agent.py 时出现类型语法相关异常。
原因：Python 版本过低，不支持依赖或 baseline 中使用的较新类型语法。
处理方式：
python --version
如果低于 Python 3.10，请重新创建 Python 3.10+ 虚拟环境：
deactivate 2>/dev/null || true
python3.10 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
不要在 Python 3.8 环境里继续排查模型或 runner 问题，先升级运行环境。
依赖安装失败
常见现象：
- No module named 'lagent'。
- 从 GitHub 安装 lagent 失败。
- 安装 ray 等依赖时时间过长或空间不足。
- 系统提示 externally-managed-environment。
处理方式：
1. 确认已经激活虚拟环境：
which python
python --version
1. 重新安装依赖：
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
1. 如果系统禁止直接安装包，使用虚拟环境或 uv venv，不要向系统 Python 强行写入依赖。
2. 如果 GitHub 访问失败，先解决网络或代理问题，再重试安装。
3. 如果磁盘空间不足，清理 pip 缓存或换到空间更充足的环境：
python -m pip cache purge
输出文件存在但 runner 跳过
现象：
Skip idx=0 because sample_outputs/0.json already exists.
原因：main.py 会跳过已经存在且非空的 {idx}.json，方便中断后继续运行。
处理方式：
- 想复用旧结果：无需处理。
- 想重新生成全部结果：删除旧输出目录。
rm -rf sample_outputs
python main.py --input_file sample_data/dev.jsonl --output_dir sample_outputs
- 想保留旧结果并做对比：换一个新的输出目录。
python main.py --input_file sample_data/dev.jsonl --output_dir sample_outputs_v2
final_response 为空
现象：输出文件中出现类似错误：
{
  "status": "error",
  "final_response": "",
  "error": {
    "type": "ValueError",
    "message": "agent.solve must return a non-empty string field: final_response"
  }
}
原因：ReasoningAgent.solve 返回的字典中没有非空字符串字段 final_response。
处理方式：
确保 solve 至少返回：
return {
    "final_response": final_answer,
    "trace": trace,
}
其中 final_answer 必须是非空字符串。不要返回数字、列表、None 或只包含中间推理的对象。
返回结果不能写入 JSON
现象：输出文件中 error.type 可能是 TypeError，错误信息包含 not JSON serializable。
原因：solve 返回值或 trace 中包含不能被 json.dump 写出的对象，例如异常对象、文件句柄、模型 SDK 原始响应对象、集合、函数或自定义类实例。
处理方式：
- final_response 使用字符串。
- trace 使用列表和字典。
- 字典中的值尽量使用字符串、数字、布尔值、None、列表或普通字典。
- 如果要记录复杂对象，先转成简短字符串摘要。
示例：
trace.append({
    "step": "model_call",
    "content": {
        "prompt_summary": "生成候选答案",
        "response": str(response_text),
    },
})
请求超时或连续重试失败
现象：错误信息包含 timeout、Read timed out、ConnectionError，或：
Chat completion failed after 3 attempts
处理方式：
- 先用 LOCAL_MAX_CONCURRENCY=1 重跑，排除并发导致的问题。
- 检查网络和代理是否能访问 API 服务。
- 减少单题模型调用次数或降低 max_tokens。
- 保留失败 JSON，查看 error.message 中最末尾的 HTTP 或网络错误。
如果连续多次只在同一题失败，检查该题是否触发了你的提示词、解析或后处理代码中的异常。
改完 user_agent.py 后完全没有变化
可能原因：
- runner 跳过了已有输出文件。
- 你修改的代码不在 PARTICIPANT DESIGN AREA 或没有被 ReasoningAgent.solve 调用。
- 当前 shell 使用的不是你刚安装依赖的虚拟环境。
处理方式：
rm -rf sample_outputs_debug
python main.py --input_file sample_data/dev.jsonl --output_dir sample_outputs_debug
然后检查新目录中的 JSON：
jq '.status, .final_response, .trace[0]?' sample_outputs_debug/0.json
如果 trace 为空或不是你预期的内容，优先检查 solve 的返回路径是否都包含你新增的记录。

获取密钥与安全管理

API Token 是调用书生 API 的凭证。请把它当作密码处理：只在本地安全环境中使用，不写入代码，不提交到仓库，也不发布到飞书文档、截图或讨论区。
获取 API Token
1. 打开 API 入口：https://internlm.intern-ai.org.cn/Api
2. 使用参赛时绑定的账号或个人账号登录。
3. 进入 API 控制台，在 Tokens 页面创建新的 API Token。
4. 创建后立即复制并保存到本地安全位置。不要把 token 粘贴到公开文档、聊天记录或代码注释中。
5. 如果有多台机器或多个实验用途，建议分别创建 token，便于后续撤销和排查异常调用。
如果控制台入口、按钮名称或展示顺序发生变化，以 API Docs 和控制台当前页面为准：
- API Docs：https://internlm.intern-ai.org.cn/api/document
- 用户鉴权：https://internlm.intern-ai.org.cn/doc/docs/%E7%94%A8%E6%88%B7%E9%89%B4%E6%9D%83/
配置到 baseline
在运行本地 baseline 前，进入 challenger_agent_baseline 目录，并在当前 shell 中设置环境变量：
cd challenger_agent_baseline
export INTERN_API_KEY="YOUR_API_TOKEN"
INTERN_API_KEY 建议填写 token 本体。baseline 的 llm_client.py 会自动生成请求头：
Authorization: Bearer YOUR_API_TOKEN
如需显式覆盖默认 endpoint 或模型，可以继续设置：
export INTERN_API_BASE="https://chat.intern-ai.org.cn/api/v1/chat/completions"
export INTERN_MODEL="intern-s2-preview"
首次调试建议把本地并发降到 1，避免代码还未验证时触发流控：
export LOCAL_MAX_CONCURRENCY=1
以上 export 只对当前终端会话生效。新开终端后需要重新设置，或使用你自己的本地环境变量管理方式加载。无论使用哪种方式，都不要把包含 token 的文件提交到仓库或提交包。
直接调用 API 时的鉴权头
如果你绕过 baseline，直接用 curl、requests 或其他 SDK 调用 OpenAI-compatible Chat API，需要自己设置鉴权头：
curl -X POST "https://chat.intern-ai.org.cn/api/v1/chat/completions" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${INTERN_API_KEY}" \
  -d '{
    "model": "intern-s2-preview",
    "messages": [
      {"role": "user", "content": "请用一句话说明本接口是否可用。"}

    "max_tokens": 128
  }'
Claude-like API 使用不同鉴权头 x-api-key，不能复用上面的 Authorization 写法。两类接口的差异见 接口调用与模型选择。

- 不要把 token 放进浏览器端代码或会被公开访问的配置文件。
- 不要在 trace、异常信息或调试输出中打印完整 token。
- 不要把 token 发到飞书群、issue、论坛或公开答疑文档。
- 如果使用 .env、direnv 或 shell profile 管理本地变量，确认相关文件不会进入提交包。
- 为不同用途拆分 token，便于在发现异常时只撤销受影响的凭证。
泄露或失效后的处理
如果你怀疑 token 已泄露，或发现 Dashboard 中出现异常调用量：
1. 立即进入 API 控制台的 Tokens 页面撤销或删除相关 token。
2. 创建新的 token，并只更新本地环境变量。
3. 检查最近提交、日志、截图、压缩包和飞书文档，确认没有继续暴露旧 token。
4. 重新运行本地样例，确认新 token 可用。
如果接口返回鉴权失败、token 过期或业务不匹配等错误，优先检查：
- INTERN_API_KEY 是否已经在当前终端设置。
- 调用 OpenAI-compatible Chat API 时是否使用 Authorization: Bearer ...。
- 是否把 Claude-like API 的 x-api-key 写法误用于 Chat API，或反过来使用。
- endpoint 是否为当前接口文档中对应的地址。
- token 是否来自当前 API 控制台账号和服务。

Baseline 的请求量来源
baseline 的 ReasoningAgent 默认配置在 user_agent.py 中：
policy_sample_times = 3
verifier_voting_times = 2
默认流程是：
1. 每题生成 policy_sample_times 个候选答案。
2. 对每个候选答案调用验证器 verifier_voting_times 次。
3. 选择置信度最高的候选作为 final_response。
因此默认每题模型调用次数约为：
3 + 3 * 2 = 9
更一般地：
每题调用次数 = policy_sample_times + policy_sample_times * verifier_voting_times
如果输入有 N 道题，默认至少会产生约 9 * N 次模型调用；网络错误或服务端错误触发重试时，实际请求数可能更多。选手自行加入多轮反思、工具调用、投票或重试逻辑后，也需要重新估算。
首次运行建议
首次跑通样例时，先把并发降到最低：
export LOCAL_MAX_CONCURRENCY=1
建议按以下顺序扩大实验：
1. 用 1 到 3 道样例题确认输出结构正确。
2. 保持 LOCAL_MAX_CONCURRENCY=1，增加题目数量，观察是否有超时或异常消耗。
3. 小幅提高并发，例如从 1 调到 2 或 4。
4. 如果触发频率限制，先降低并发、减少采样次数或验证次数，再评估是否需要申请更高流控。
降低调用压力的常用方式：
- 降低 LOCAL_MAX_CONCURRENCY。
- 降低 policy_sample_times 或 verifier_voting_times。
- 降低 max_tokens，尤其是验证器这类短输出场景。
- 缩短提示词和 trace 中会再次送入模型的内容。
- 对可恢复错误使用有限重试，避免无限循环重复请求。
申请更高流控
当本地逻辑已经验证正确，但实验规模确实需要更高 RPM / TPM 时，可以提交流控申请：
1. 打开流控申请页面：https://internlm.intern-ai.org.cn/api/strategy
2. 按页面要求填写账号、用途、期望额度等信息。
3. 用途中说明与“挑战杯”参赛实验相关。
4. 尽量给出可复核的估算依据，例如题目数量、每题调用次数、并发数、预计运行时间。
5. 提交后等待审批和额度生效；具体审批规则以平台当前说明为准。
申请前建议先准备一份简短估算：
预计请求数 = 题目数量 * 每题调用次数
并发需求 = LOCAL_MAX_CONCURRENCY
主要模型 = INTERN_MODEL
单次输出上限 = max_tokens
不要为了申请更高流控而夸大并发需求。过高并发会增加排查难度，也可能放大代码中的重复请求或死循环问题。
查看使用情况
API 控制台提供 Dashboard，可用于查看调用量和 token 使用量：
- API 入口：https://internlm.intern-ai.org.cn/Api
- API Docs：https://internlm.intern-ai.org.cn/api/document
建议在以下节点查看 Dashboard：
- 首次跑通样例后，确认调用量与预期接近。
- 调整 policy_sample_times、verifier_voting_times、LOCAL_MAX_CONCURRENCY 或 max_tokens 后，观察增量变化。
- 大批量运行前，先用小批量估算单位题目消耗。
- 大批量运行中，定期确认没有异常增长。
如果调用量或 token 使用量明显高于预期，优先检查：
- 是否有异常重试、死循环或重复提交同一题。
- 输出目录中已有结果是否被正确跳过。
- max_tokens 是否设置过高。
- prompt 或 trace 是否不断累积，并被再次送入模型。
- 是否有多个终端、脚本或机器同时使用同一个 token。

提交评测与说明

本页说明正式评测时平台会加载什么、调用什么，以及选手提交代码时需要守住哪些边界。请先把本页读完，再根据后续页面检查提交包结构、接口返回格式和本地自测结果。
核心结论
正式评测只依赖选手提交代码中约定的智能体入口：
- 提交根目录必须包含 user_agent.py。
- user_agent.py 必须暴露 ReasoningAgent 类。
- ReasoningAgent 的构造函数必须接受 client 参数，平台会以 ReasoningAgent(client=official_client) 的方式初始化。
- ReasoningAgent.solve(problem: str, metadata: dict) -> dict 必须可被调用。
- solve 必须返回 dict，并包含非空字符串字段 final_response。
- 推荐同时返回 trace，用于记录关键推理步骤、模型调用摘要、候选答案、验证过程和异常排查线索。
最终评测主要依据 final_response 的答案正确性。trace 是推荐的诊断与设计参考信息，不能替代 final_response，也不要把敏感信息写入 trace。
本地样例与正式评测的区别
baseline 中的 main.py 和 llm_client.py 用于帮助选手在本地跑通样例数据：
- llm_client.py 是本地样例 API client，便于理解如何调用书生 API。
- main.py 是本地样例 runner，负责读取样例 JSONL、调用 ReasoningAgent.solve、写出结果 JSON。
- sample_data/dev.jsonl 是本地调试样例，可能包含用于对照调试的字段。
正式评测不会使用选手提交的 main.py 或 llm_client.py 作为评测入口。平台会加载选手提交的 user_agent.py，使用官方 client 初始化 ReasoningAgent，再由官方 runner 调用 solve(problem, metadata)。
因此，选手可以修改或替换本地调试脚本，但不能改变正式评测需要的入口契约。只要 user_agent.py 与相关依赖满足规范，本地 runner 的具体实现方式不会影响平台调用边界。
官方评测会补充什么
正式评测环境会在不改变选手智能体接口的前提下，补充本地样例脚本中未完整覆盖的平台能力。可能包括：
- 隐藏测试集读取与题目 metadata 注入。
- 官方 API client、鉴权、请求重试、超时控制、限流管理和 token 统计。
- 并发调度、资源隔离、单题超时和全局运行控制。
- 返回值结构校验、JSON 序列化校验和错误归一化。
- trace 收集、截断、脱敏、存储和展示。
- 官方 judger 对接、结果汇总和榜单写入。
这些能力由平台统一处理。选手代码只需要实现清晰、稳定、可导入的智能体逻辑，不需要在提交包中实现正式评测系统。
不要依赖的内容
为了保证代码能在平台环境中稳定运行，请避免以下依赖：
- 不依赖本地机器的绝对路径，例如 /home/...、/Users/... 或某个个人目录。
- 不依赖未提交到仓库中的隐藏文件、缓存文件、临时输出或私有配置。
- 不依赖样例数据中的 answer 字段；正式评测不会向 solve 传入标准答案。
- 不依赖题目固定顺序，也不要假设 idx 连续或从 0 开始。
- 不依赖多个题目一定在同一个进程、同一个线程或同一个 ReasoningAgent 实例中运行。
- 不依赖选手自己的 main.py 或 llm_client.py 会在正式评测中被使用。
- 不依赖官方 client 的内部私有字段，只使用约定的调用方式组织模型请求。
推荐阅读顺序
如果你正在准备提交，建议按以下顺序检查：
1. 提交包结构与依赖规范
2. ReasoningAgent 接口与返回格式
3. 官方 Client 与 Runner 说明
4. 提交前自检清单

ReasoningAgent 接口与返回格式
正式评测平台通过固定接口调用选手代码。本页明确 ReasoningAgent 的初始化方式、solve 输入参数、返回字段和常见错误。请把这里的接口契约视为提交代码必须满足的最低要求。
初始化接口
平台会从提交根目录的 user_agent.py 中导入 ReasoningAgent，并传入官方 client：
from user_agent import ReasoningAgent

因此，构造函数至少需要接受 client：
class ReasoningAgent:
    def __init__(self, client, *args, **kwargs):
        self.client = client
初始化阶段建议只完成轻量、确定性的准备工作，例如保存 client、加载随提交包提供的提示词模板、初始化小型配置。请避免在初始化阶段执行以下操作：
- 读取隐藏数据、标准答案或平台内部文件。
- 访问本地个人路径或未提交的私有配置。
- 执行耗时很长或不稳定的外部请求。
- 假设所有题目都会复用同一个进程、线程或 agent 实例。
推理接口
ReasoningAgent 必须提供：
def solve(self, problem: str, metadata: dict) -> dict:
    ...
参数含义：
- problem：数学题题面文本。
- metadata：题目元信息字典，可能包含 idx 等平台注入字段。
使用建议：
- 可以使用 metadata.get("idx") 标记日志或 trace，但不要依赖 idx 连续、固定或从 0 开始。
- 不要读取或依赖 metadata["answer"]。样例数据中可能出现 answer 方便本地对照，正式评测不会向 solve 提供标准答案。
- 单题求解逻辑应尽量自洽，不要依赖前一题的运行结果或题目顺序。
- 遇到可恢复的模型调用异常时，可以在内部重试或记录诊断信息；最终仍需返回符合格式的结果，或让异常被平台 runner 捕获并归一化。
必须返回字段
solve 必须返回 dict，且必须包含非空字符串字段 final_response：
{
  "final_response": "最终答案"
}
final_response 要求：
- 类型必须是 str。
- 去除空白后不能为空。
- 内容应是面向判分的最终答案，而不是完整日志、Python 对象或异常堆栈。
- 建议在内部完成答案抽取和格式化，避免把冗长推理过程直接作为最终答案。
正式评测主要依据 final_response 的答案正确性。请确保它表达清晰、格式稳定，并且不依赖人工再解释。
推荐返回字段：trace
推荐同时返回 trace，用于记录智能体的关键推理和诊断信息：
{
  "final_response": "最终答案",
  "trace": [
    {"step": "plan", "content": "识别题型并制定解题策略"},
    {"step": "model_call", "content": "生成候选答案摘要"},
    {"step": "verify", "content": "检查候选答案并选择最终结果"}
  ]
}
trace 建议：
- 使用列表或简单字典结构，确保可以 JSON 序列化。
- 记录关键策略、中间结果、模型调用摘要、候选答案、验证过程和错误排查线索。
- 控制体积，避免写入完整无关日志、超长原始响应或大量重复内容。
- 不要包含 API key、访问令牌、个人隐私、平台内部信息或其它敏感内容。
trace 是推荐的诊断与设计参考信息。它有助于定位错误、展示方案思路和理解异常，但不能替代 final_response。
JSON 序列化要求
返回值需要能被标准 JSON 工具序列化。以下对象不应直接放入返回值：
- Python 函数、类、异常对象、文件句柄、模型 client、生成器。
- set、bytes、Path、datetime 等未转换的对象。
- NumPy、Pandas、SymPy 等库中的复杂对象，除非已转成字符串、数字、列表或字典。
如果需要记录异常，请转成简单结构：
{
  "step": "error",
  "content": {
    "type": "TimeoutError",
    "message": "model request timed out"
  }
}
常见错误
提交前请重点排查：
- user_agent.py 中没有 ReasoningAgent。
- ReasoningAgent.__init__ 不接受 client。
- solve 返回非 dict。
- final_response 缺失、为空或不是字符串。
- trace 中包含不可 JSON 序列化对象。
- 代码从样例数据读取 answer 作为答案来源。
- 对 metadata 字段做过强假设，导致隐藏测试环境中抛错。
- 在返回值、日志或 trace 中泄露密钥、访问令牌或个人路径。
只要以上接口稳定，选手可以自由设计内部推理策略、提示词、工具调用、候选生成与验证流程。

官方 Client 与 Runner 说明

baseline 中的 llm_client.py 和 main.py 是本地调试工具，不是正式评测系统。本页说明它们与官方 client、官方 runner 的关系，帮助选手明确哪些接口可以依赖，哪些本地实现细节不能依赖。
baseline 中的本地组件
baseline 提供两个本地组件，目的是让选手快速理解调用链路：
- llm_client.py：本地样例 API client，读取环境变量并调用书生 API。
- main.py：本地样例 runner，读取样例数据、初始化 ReasoningAgent、调用 solve、写出每题结果。
它们适合用于本地自测、定位接口问题和理解输出格式。选手可以基于它们调试自己的方案，也可以编写额外脚本进行实验。
请注意：本地组件的实现细节不是正式评测承诺。正式评测只承诺按约定加载 user_agent.py、初始化 ReasoningAgent 并调用 solve(problem, metadata)。
正式评测的调用边界
正式评测不会依赖选手提交的本地 client 或 runner。平台会按类似流程执行：
1. 拉取或解压选手提交代码。
2. 安装提交包声明的依赖。
3. 从 user_agent.py 导入 ReasoningAgent。
4. 使用官方 client 初始化：ReasoningAgent(client=official_client)。
5. 读取隐藏测试题，构造 problem 和 metadata。
6. 使用官方 runner 调用：agent.solve(problem, metadata)。
7. 校验返回值，收集 final_response、trace、异常信息和运行统计。
选手提交包可以包含 main.py、llm_client.py 或其它本地调试文件，但不能假设这些文件会被正式评测系统调用。
官方 client 可能补充的能力
官方 client 会在平台侧统一管理模型访问。相较本地样例 client，正式评测中的 client 可能补充：
- 统一鉴权和模型访问策略。
- 请求重试、退避、超时控制。
- RPM / TPM 流控管理。
- token 使用统计和资源记录。
- 错误码归一化。
- 敏感信息脱敏。
选手代码应只依赖公开约定的调用方式，例如使用 client.chat(messages, temperature, max_tokens) 组织模型请求。不要读取 client 的内部属性，不要修改 client 的鉴权信息，也不要假设正式 client 与本地样例类拥有完全相同的私有实现。
示例：
response = self.client.chat(
    messages=[
        {"role": "user", "content": problem},
    ],
    temperature=0.2,
    max_tokens=4096,
)
官方 runner 可能补充的能力
官方 runner 会在平台侧统一管理题目、运行环境和输出校验。相较本地样例 runner，正式评测中的 runner 可能补充：
- 隐藏测试集加载与 metadata 注入。
- 多进程或多线程调度。
- 单题超时、全局超时和资源隔离。
- 输出 schema 校验与 JSON 序列化校验。
- 异常捕获、状态记录和错误归一化。
- trace 截断、脱敏、收集和展示。
- 评测结果收集、官方 judger 对接和榜单数据写入。
这些能力不要求选手自行实现。选手需要保证自己的 solve 在单题输入下能稳定返回规范结果，并且不会依赖本地 runner 的私有行为。
对选手代码的实际要求
请按以下原则编写提交代码：
- 保持 ReasoningAgent 和 solve 的接口契约不变。
- 将复杂推理逻辑封装在 user_agent.py 或随提交包一起提供的辅助模块中。
- 使用相对路径读取随包资源，不读取个人电脑上的绝对路径。
- 不假设正式 client 暴露本地样例 client 的内部字段。
- 不假设正式 runner 会按固定顺序、固定并发方式或固定进程模型调用题目。
- 不从样例数据、输出目录或本地缓存中读取标准答案。
- 在本地样例上确认 final_response 非空、返回值可 JSON 序列化、trace 不含敏感信息。
本地跑通是正式提交的必要准备，但不是正式评测环境的完整复制。请以本系列文档中的入口契约作为最终提交标准。
